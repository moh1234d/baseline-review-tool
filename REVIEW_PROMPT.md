# Task: independent review, logic audit and improvement plan for the "Baseline Review Tool" (v7.8)

You are a senior reviewer with two backgrounds: (1) a planning/scheduling expert who reviews Primavera P6 baselines and updates for a Project Management Consultant (PMC) in Saudi Arabia, and (2) a senior JavaScript engineer. Be critical and independent. I want faults, risks, wrong assumptions and gaps found, not praise.

You will receive: this prompt, a zip with the tool (source, built HTML, tests, a Node runner), and ONE real P6 XER export of a live project (about 32,000 activities, several contractors, a hotel fit-out). The XER is not in the zip. Treat it as confidential project data: use it only for this review and do not quote more of it than needed to show a finding.

The person who will act on your report is another AI (Claude) that edits this code base. Write so that it can implement your findings exactly, without guessing (see "Deliverable").

## 1. Context
- Owner: Senior Planning Engineer at a PMC, Gulf/Middle East practice (FIDIC-style contracts, Saudi calendars with Friday-Saturday weekend and Eid/National Day/Foundation Day holidays, one 8-hour day, no shifts). Ignore UK-only practice unless it is also normal in the Gulf.
- Purpose: cut the time and effort of reviewing baselines and weekly/monthly updates across many projects. Quick, accurate, efficient. A reviewer should reach a defensible list of findings in minutes. The largest schedule is about 35,000 activities.
- One project per XER, but a project can have several contractors, vendors and suppliers. Activity names are English. "Critical" means total float of zero or less; the longest path is the most critical.
- The tool is ONE self-contained HTML file built from `src/` by `build.py`. It runs in the browser; files are not uploaded. Optional Claude AI features are off by default.
- Standing rules that every proposal must respect: every setting is configurable in both the phone and web UI, never hard-coded; every delivered file is versioned in its name and visible inside the tool; sample baselines are not standards; no project data in the repository; the findings must be framed as "to check with the contractor", never as entitlement or EOT conclusions.

## 2. How the tool works (the reasoning you are auditing)
Pipeline: `parseXER` (engine1) -> `buildModel` (tables to tasks, links, calendars, WBS, codes, resources; actual dates used for completed work) -> `applyCategories` (stage per WBS) -> `E.run` (check library: T = contract/time rules, L = logic and schedule hygiene, others for resources, cost, calendars) -> results with status pass/fail/notrun, count, evidence.
- **Structure detection** (engine11, `E.structure`): for each activity it derives building, package/unit, zone, floor, trade, contractor and stage. Priority: user-chosen activity code, else automatic code suggestion by code-type name, else WBS path words, else activity-name keywords. Settings live in `S.cfg.structure` (codeMap, unitWords, unitSkipParents, bareBuilding, floorStrict, zoneSystem, contractorAliases, tradeRules, stageRules).
- **Sequence rules** (engine12, `E.seqCheck`): each activity is mapped to a step (for example plaster, ceiling, paint, door leaves and joinery) by keywords; rules compare a predecessor step with a successor step inside the same floor/zone scope and flag missing logic, date overlap or odd relationship types; a floor-direction check tests whether work moves up or down the building; a same-trade-in-several-places check looks for parallel work with no link.
- **Schedule comparison** (engine6, engine13, engine14, engine15): previous vs current XER; key-date movement, driving path (engine7 `dlDrivers`), recovery options (`E.recalc` simplified forward pass, retained logic), update checks (BEI, CPLI, missed activities, out-of-sequence progress, percent complete vs remaining duration, actuals after the data date), audience-specific wording (contractor, consultant, PMC). Large pairs run in a background worker (blob built from `ENGINE_SRC`).
- **Delay analysis**, **Claim review** (notice period counted from the event date, assumed to be the awareness date; user can switch to event end), **Baseline builder** (BOQ to activities with productivity rates), **P6 roundtrip check**, **Portfolio triage** (many XERs, one ranked table), **carry-over of findings** between reviews (activity-level keys kept for the last three reviews), Word/Excel/brief outputs, and a Cloudflare Worker with a password gate.
- Known limits stated by the owner: the recalculation ignores resource limits and applies only start constraints; the comparison was tested only on synthetic pairs and unit fixtures; AI paths were tested only with a mocked API; the Worker gate was not tested live.
- A first comparison on this same project already led to fixes in v7.7/v7.8 (B1/B2 read as buildings, no contractor dimension, door step counting submittals, floor groups read as packages). Do not just re-report those; check that they are fixed and look for the next layer of faults of the same kind.

## 4. What to assess
A. **Logic and reasoning against the real XER.** For each check family (L, T, others), sequence rules, structure detection, trade/contractor/zone/floor grouping, stage detection, step keywords: is the tool's result right, partly right, or wrong for this project? Give counts of false positives and false negatives where you can. Which checks would a Gulf PMC reviewer expect and the tool lacks? Which findings are noise for a multi-contractor, activity-code-driven schedule?
B. **Scheduling correctness.** XER parsing (multi-project files, calendars, lags, relationship types, constraints, resources); the simplified CPM recalculation and driving-path logic (calendars, lags, constraints, retained logic vs progress override, out-of-sequence progress, negative float); update checks (BEI, CPLI definitions, thresholds); delay and recovery wording.
C. **Performance and robustness.** Time and memory on this 32k-activity file and a 35k pair; the browser freezing; anything else that should move to a Web Worker; malformed or partial files; odd encodings; XSS from file text rendered with innerHTML; where data could leave the device.
D. **Usability and weekly workflow.** Time to first useful result; the Quick review tabs; the Order of the trades views; phone use; what is missing for someone reviewing 10-30 projects a month.
E. **Code quality.** Structure (concatenated JS parts, global state `S`), duplication, dead code, hard-coded values that should be settings, testability. Propose a minimal automated test plan using synthetic fixtures only.
F. **Reports and outputs (content accuracy).** Are the Word report, brief and Excel appendix accurate and not misleading?
G. **Appearance, charts and visual design.** Open the built HTML in a browser at desktop width and at phone width (about 400 px) and, if you can, in dark mode. Review every screen: navigation, Quick review tabs, Order of the trades (month strip and cards), comparison tables, delay views, portfolio table, builder and claims split layouts, and the Word/Excel outputs' look. Look for: overlapping or clipped labels and bars, unreadable colour contrast, charts that mislead (truncated axes, bars that all look full, unclear scales), tables too wide for a phone, inconsistent spacing/typography, poor hierarchy (what to read first), missing legends or units, accessibility (contrast, colour-only meaning, tap-target size), and print/export look. Palette in use: navy #1B2A41 and teal #0B7A75. For each issue give a screenshot description or the exact screen, the CSS/JS location (`src/shell.html` or the `app*.js` function), and a concrete fix (CSS or code). Propose better chart types for the data (timeline/Gantt strips, float histograms, driving-path ribbons, S-curves, trade-by-floor heat maps, portfolio ranking visuals) and a consistent chart style. Any visual setting must be configurable on phone and web.
H. **Enhancements and new ideas.** Each with benefit, effort (S/M/L), risk and the data it needs. Consider at least: automatic detection of project conventions (a "profile" per client/contractor that remembers code mappings), production-rate checks against quantities, resequencing options, S-curve and cash flow, schedule-quality score trend, learning from reviewer decisions, a faster first screen, better use of AI (and what must never be sent), and anything that lowers review time per project.
